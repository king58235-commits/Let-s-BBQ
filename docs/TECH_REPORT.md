## 1. 專案概況

- **玩法**：客人從右側走進櫃台排隊，頭上氣泡是點單（順序要一模一樣）；玩家串好放上 6 格烤架，看熟度條（太生→有點沒熟→熟了→完美→焦了），拿起來交給客人；焦了或串錯可丟垃圾桶。
- **壓力曲線**（`CFG.phases`）：出客間隔 9→2.4 秒、同時在場 2→5 位、點單長度 2→4 個食材，78 秒起「最後衝刺」；點單越複雜分數倍率越高（×1／×1.7／×2.6）。
- **技術**：Canvas 2D、邏輯解析度 540×960 等比縮放、Pointer Events（滑鼠＋觸控共用）、Web Audio 合成音效、`navigator.vibrate`、`localStorage` 存設定。
- **檔案**：見 README；重點是 `index.html`（遊戲）、`assets/`（17 張成品）、`assets/raw/`（Codex 原圖與封存，36 MB）、`tools/`（去背、檢查、測試、Codex 協作工具）、`ASSETS.md`（美術規格與角色名單）。

### 時間線（大致順序）
1. 討論玩法 → 色塊原型（先證明好玩再做美術）。
2. 美術風格探索（5 輪，見 §4.4）→ 批次生成 → 大小校準、去背、接進遊戲。
3. 真實使用者回饋驅動的調整：獸臉化、角色比例、食材色相、UI 風格（先參考公司專案，後改為獨立的夜市燈籠風）、客人排隊制。
4. 音效 → 壓力曲線 → 手感包（粒子、震動、安全區域）→ 自動化測試。

## 2. 架構

**單一 HTML、無框架**。理由：可雙擊開啟、可直接放 GitHub Pages、AI 一次讀得完。代價是檔案長（1614 行），後期每次讀檔都吃上下文（見 §5）。

| 區塊 | 內容 |
|---|---|
| `CFG` / `INGREDIENTS` / `CUSTOMERS` | 所有數值與資料集中在檔案開頭，調平衡只改這裡 |
| 版面 `L` / `QUEUE` | 邏輯座標；點擊判定、繪圖共用同一份矩形 |
| 狀態 `G` | `title / playing / over` + `paused`；`update(dt)` 只推進遊戲，繪圖與邏輯分離 |
| 輸入 | 一個 `onTap(x, y, drop)` 處理滑鼠／觸控／拖放；鍵盤是另一組對應到同樣的動作函式 |
| 繪圖 | `drawScene()`：背景 → 客人本體 → 櫃台 → 客人 HUD（氣泡、耐心條）→ 烤架 → 組裝列 → 托盤 → HUD → 特效 → 彈出字 → 手上的串 → 暫停／結算 |
| `Haptic` / `FX` / `Sound` | 震動、粒子與畫面震動、音效引擎；`Sound.play(name)` 會順便觸發同名震動 |
| 素材 | `ART_FILES` 對照表＋`ASSET_VER` 版本戳（見 §7） |

**幾個值得留用的設計**
- **佔位圖優先**：沒有圖時自動退回 emoji／色塊，所以美術可以隨時一張張換進去。
- **所有「看得見」的事件都有對應的函式**（`fxServe`、`Sound.play('perfect')`…），掛在邏輯上而不是繪圖裡，所以測試可以直接驅動邏輯、不必看畫面。
- **`window.__manualSim`**：測試頁設定後，遊戲自己的影格迴圈不推進時間，也不發聲、不震動。

## 3. 美術管線

```
Claude 寫任務檔 ─→ codex exec 生成（綠幕 #00FF00）─→ assets/raw/
      ↑                                              │
      │      check_raw.py（尺寸、背景、貼邊、亮度）←──┤
      │                                              ↓
 退件（附被退的圖＋原因）←── Claude 目視審查 ←─ process_assets.py（去背、依頭部對齊裁切、縮圖、更新版本戳）
                                                      ↓
                                               assets/ → 接進 ART_FILES → 並排校準大小
```

- **綠幕而非透明背景**：圖像工具的透明輸出不穩定；用純綠 `#00FF00` 再由腳本去背。副作用：角色身上不能有偏綠的顏色（薄荷綠點綴差點被當成背景吃掉，spill 值 57～63 vs. 背景 255，所以去背門檻要避開）。
- **客人立繪依「頭部」自動對齊**：頭在圖的水平正中央、頭頂貼齊上緣、身體左右完整保留（不固定寬度裁切——這是我早期的錯，見 §7）。
- **三種風格各管各的**：客人＝手遊立繪風；食材＝Q 版水彩；UI＝平面色塊＋圖形元件。風格規格在 `ASSETS.md`。

## 4. Claude ↔ Codex 協作

### 4.1 分工

| | 做什麼 | 不該做什麼 |
|---|---|---|
| **人** | 方向、品味（「有 AI 味」「假立體」「太像」）、取捨 | 逐張檢查技術規格 |
| **Claude** | 寫規格與任務檔、下指令、審查、退件理由、後製腳本、整合、測試、記錄 | 判斷「好不好看」的最終裁決 |
| **Codex** | 生圖；必要時用 Python 縮放／校正背景 | 自己評斷風格（它不會挑剔） |

### 4.2 協作協定（可直接重用）
- 呼叫：`codex exec -C <專案> -s workspace-write --skip-git-repo-check -c 'model_reasoning_effort="medium"' -i <參考圖> [-i <第二張>] -o <最後訊息檔> --json - < 任務.txt`
- **任務檔結構**（`tools/codex/TASK_TEMPLATE.md`）：①硬性規則（只能新增哪一個檔、不准動別的）②授權（可用程式縮放／校正背景，**不需詢問**）③風格（附範本圖）④內容⑤回報格式。
- **參考圖**：核准過的圖當風格錨點；退件重做時再附「被退的那張」並寫明原因，說「保持同一角色，只改 X」。
- **平行**：`xargs -P 2~3`；每個任務各自的 `.jsonl`（事件與用量）、`_last.txt`（最後訊息）、`.err`。
- **非互動模式的陷阱**：Codex 遇到不確定會**停下來問**，但沒人能回答，結果是「空手結束」（見 §4.5）。

### 4.3 審查流程（兩道關）
1. **客觀檢查**（`tools/check_raw.py`，幾乎不花上下文）：尺寸、四角是否純綠、主體是否貼邊或被畫布切到、平均亮度、鋪滿型圖不該含綠幕。
2. **目視審查**（花上下文，所以只對通過第一關的圖做）。
- 退件的檔案**不刪除**：改名加後綴（`_v6_humanface`、`_rejected`、`_retired`…），保留比較與可回頭。

### 4.4 結果統計
36 個原圖 → 17 張成品、19 張被封存（含 1 張是成品的重複檔）。

| 被封存的原因 | 張數 | 性質 |
|---|---|---|
| 人改變方向：半獸人→獸臉（6）、風格改版（bear 水彩／平塗 2）、食材平塗被否決（1）、食材換成色相差大的（香腸、香菇 2） | **11** | 設計決定，不是失敗 |
| 模型／構圖／規格：身體被畫布切掉、姿勢僵硬×2、點綴色撞色、香菇像麵包、豬肉過度寫實＋帶竹籤、狐狸與狼太像 | **7** | 品質問題 |
| 重複檔 | 1 | — |

**風格方向的反覆（客人）**：水彩半獸人 → 平塗半獸人 → 手遊立繪風（參考幹員立繪特徵）＋人臉獸耳 → 全獸臉（Lv3）。每改一次，8 位角色就要全部重來。

### 4.5 失敗模式目錄

| 症狀 | 原因 | 對策 |
|---|---|---|
| 執行結束但沒有檔案，最後訊息是「請問可以縮放嗎？」 | 非互動模式遇到不確定就問（工具輸出 1254×1254、背景有色差） | 任務檔**預先授權**「可用程式縮放、校正背景，不需詢問」 |
| 食材圖自帶一根直竹籤 | **我的規格寫了「串在籤上」** | 規格要寫「不要畫竹籤」；規格錯誤要自己認 |
| 豬肉過度寫實、油亮 | 沒附風格範本 | 一定附已核准的圖 |
| 人物左右被畫布切掉 | 生成時就太滿 | 任務檔寫死「左右各留 7%」；`check_raw.py` 自動抓 |
| 點綴色撞色（兔青藍 vs 狼冰藍） | 規格寫了顏色，模型偏了 | 退件時附原圖，「只改顏色」；一次就修好 |
| 姿勢僵硬（雙手垂在身前交握） | 沒指定姿勢 | 任務檔**指定具體姿勢**，並禁止常見的僵硬姿勢 |
| 兩個同科角色太像 | 只換臉，其他都一樣 | 姿勢、體型、髮型、衣服底色一起換；新增角色先並排看剪影 |
| 同一批角色大小不一 | 各張的臉畫得大小不同 | 附統一範本、寫頭部占圖高比例；遊戲端再用 `scale` 係數並排校準 |
| 食材烤熟後都變咖啡色、難分辨 | 設計時色相太近 | 選色相差大的食材（紅綠黃紫），並在氣泡加顏色底圈 |

### 4.6 有效與無效
- **有效**：參考圖（風格、大小、構圖）；綠幕＋自動去背；退件時「保持角色、只改 X」；先客觀檢查再目視；`medium` 推理強度（這個任務幾乎不需要推理）；Codex 對**事實**的回報可信（路徑、尺寸、有沒有動別的檔案）。
- **無效／不可靠**：Codex 對**風格**的自評；用文字描述「不要像 AI」（要靠參考圖與人的判斷）；沒有鎖定風格就批次生成。

## 5. 用量分析（Claude vs. Codex）

**使用者回報的數字**：Codex 五小時額度 66%、週額度 10%；Claude 五小時約 20～30%、週額度 11%。（本報告撰寫時 Claude 週額度顯示 12%，Team 方案，五小時視窗剛重置。）

### 5.1 Codex 端：我能量到的
我保留了 24 份執行紀錄（`--json` 事件，含 `turn.completed.usage`），涵蓋 37 次執行中的 24 次（其餘被後來同名任務覆蓋）；其中 23 份完整（1 份是我中途叫停）。

| | 合計（23 次） | 平均／次 |
|---|---|---|
| 輸入 tokens | 7,939,374（**88.9% 為快取**） | 345,190 |
| 輸出 tokens | 73,171 | 3,181 |
| 推理輸出 tokens | 8,660 | ~380 |
| 指令 | 110 次（讀技能說明 24、Python 後製 48、檢查 38） | ~4.8 |

- 單次輸入最小約 13 萬（固定成本：讀 `imagegen` 技能說明＋系統提示），附兩張參考圖或多次檢查的可到 90 萬～136 萬。
- **推理幾乎為零** → `model_reasoning_effort` 設 medium 或 ultra 對這類任務沒有實質差別（但你原本的預設是 `ultra`，我覆寫成 medium 是對的）。
- 外推全部 36 次完整執行：輸入約 1,240 萬、輸出約 11 萬 tokens。

### 5.2 為什麼 Codex 花了 66% 的五小時額度？（推論，非實測）
- 文字 token 少得可憐（平均輸出 3k），**所以額度不是花在文字上**。
- 紀錄裡**看不到圖像生成的用量**（事件只有 `agent_message` 與 `command_execution`；內建 `imagegen` 工具不出現在 token 帳裡）。最合理的推論是：**額度主要被「生圖」本身吃掉**。我沒辦法直接證明，因為看不到 Codex 的額度帳本。
- 粗估單張成本：37 次執行約產出 40～50 張圖（有些執行生成兩次；兩次空手結束的執行也各生成了一次但沒存），所以約 **每張 1.3～1.7% 的五小時額度、0.2～0.25% 的週額度**。*這是用你的百分比除以我估的張數，不是量到的。*
- 五小時 66%、週 10% 的比例，代表這是**短時間密集使用**造成的壓力，不是整週用量大。

### 5.3 Claude 端：我能量到的
- 本對話上下文：**926,341 / 1,000,000 tokens（93%）**；其中對話歷史 852,876（85%）、系統工具 37,782、MCP 工具 20,744、系統提示 9,706。
- 模型 `claude-sonnet-5-5`、推理強度 `high`、對話時長約 5 小時 15 分。
- **推論**：Claude 的用量不是來自「輸出」，而是來自**每一輪都要重讀整段上下文**。上下文裡大量是截圖、重複讀取的 1600 行檔案、冗長的工具輸出。對話越長，每一輪越貴。

### 5.4 兩邊的成本結構（一句話版）
- **Codex ≈ 生圖張數**（重做一次就是整張重付）。
- **Claude ≈ 上下文長度 × 輪數**（截圖與重讀大檔最傷）。

### 5.5 本次可避免的浪費
| 項目 | 次數 | 屬於 |
|---|---|---|
| 方向改變造成整批重做 | 11 張 | Codex |
| 沒預先授權而空手結束 | 2 次執行 | Codex（我的指令問題） |
| 使用者改變心意而中途叫停 | 1 次 | Codex |
| 規格錯誤／缺指定（竹籤、姿勢、相似度） | 約 2～3 次 | Codex |
| **合計** | **約 14～17 / 37 次（≈ 4 成）** | |

Claude 端：每個畫面都截圖確認（我數次用 0.1 倍縮圖＋再截全圖＝兩張）、反覆分段讀同一個大檔、把完整測試輸出貼回上下文。

### 5.6 降低用量的作法
**Codex**
1. **先鎖風格再批次**：先出 1 張主角圖，在小尺寸下看過（含「縮成圖示還認得出來嗎」），人確認方向後才批次。
2. **任務檔一開始就寫完整**：授權、姿勢、禁止事項、參考圖——避免空手結束。
3. **一次一個任務多張圖**（若工具支援）以攤平每次約 13 萬的固定輸入成本；**不要要求 Codex 自己審查**（我自己會審，它的檢查指令只是重複花費）。
4. 參考圖別附太多（附兩張的執行輸入可到 130 萬以上）。
5. **做一次校準實驗**：記錄額度前後百分比，跑「一次 5 張」×3 次，才能得到真正的每張成本。

**Claude**
1. 把專案分段：每個里程碑結束就寫報告＋記憶，**開新對話**（本報告就是這樣做的）。
2. **少截圖**：用 JS 讀狀態、跑測試取代；截圖留給最終確認，並一次只拍一張。
3. 大檔拆成小模組，避免每次讀 1600 行；用搜尋定位後只讀需要的片段。
4. 審查多張圖時做**聯絡表**（把一批圖縮成一張帶檔名的拼圖，一次看完）——這是我沒做、下次應該做的。
5. 測試輸出只回傳摘要。

## 6. 品質保證

**`tools/test.html`（12 項）**：素材與設定、音效名稱對照、音效引擎、音效保護、壓力曲線單調、稱號門檻、遊戲流程冒煙、交餐與計分、隨機壓力測試、機器人難度曲線、繪圖冒煙、特效／震動／安全區域。

- **機器人難度曲線**：用不同「每動作秒數」的機器人（0.45／1.0／1.4）驗證分數單調、開局不掉客人、衝刺期有壓力。**重要限制**：機器人無思考時間，是專家上限，不代表真人。
- **突變測試**：故意弄壞 8 個地方（倍率、曲線、素材、繪圖、重複頭像、門檻、粒子上限、安全區域），**8 個全被抓到**——用來證明測試不是空轉。
- **繪圖冒煙測試**：繪圖錯誤只會在畫面上看見，所以把每種畫面狀態都畫一遍，確認不丟例外。
- 全部測試**靜音**，且**不得改動使用者設定**（見 §7）。

## 7. 踩雷與教訓（工程）

| 事件 | 教訓 |
|---|---|
| **測試透過使用者的喇叭播放**，把一整局壓縮在 37 毫秒內跑，同時發聲 864 個（真實遊玩最高 20）→ 爆音 | 預覽視窗是真的會出聲。自動化測試必須靜音；時間壓縮的測試會讓所有事件「同時」發生 |
| **亂點的壓力測試點到設定按鈕**，把音效、音樂、震動永久關掉；而預覽視窗和玩家**共用 localStorage** | 測試前後要比對並還原設定；守門員本身也要用突變測試驗證 |
| 引擎本身沒有保護，狂點按鈕會疊爆 | 同時發聲上限（32）＋同名最小間隔 |
| **瀏覽器快取**讓人看到舊的角色圖 | 圖片網址帶版本戳，由處理腳本自動更新 |
| 隱藏的預覽視窗**不執行 `requestAnimationFrame`** | 測試要自己推進時間並手動繪圖；別把「畫面沒變」當成 bug |
| 我用固定寬度裁切角色，**切掉身體兩側**（熊 150 px、羊 88 px） | 依角色的頭部對稱裁切、保留整個身體；用數字量化問題再修，不要憑感覺 |
| 交付檔裡的 Windows 路徑被 shell 跳脫成亂碼（`\a`、`\r`） | 路徑一律用正斜線；寫入後讀回來檢查 |
| 背景任務最後加 `&` 會讓通知提早觸發 | 要等結果就不要把工作丟到子 shell 背景 |
| 縮放角色時固定頭頂位置→人物飄起來或陷進櫃台 | 以櫃台為基準錨定下緣 |
| 薄荷綠被去背吃掉 | 去背門檻要避開「偏淡的綠」 |
| Codex 是 Store 版 App，執行檔在受保護資料夾；npm 版 CLI 裝好後我的 shell PATH 還是舊的 | 用完整路徑呼叫 `%APPDATA%\npm\codex.cmd`；確認後才下指令 |

## 8. 下個專案的作法（Playbook）

1. **討論 → 色塊原型**，先證明好玩；數值集中在 `CFG`。
2. **鎖風格**：每一類美術各出 1 張，人看過（含縮小後）才批次。把風格寫進 `ASSETS.md`，並保留「範本圖」。
3. **寫任務檔**用 `tools/codex/TASK_TEMPLATE.md`，一次寫完整（授權＋禁止事項＋參考圖＋姿勢）。
4. **兩道關審查**：`check_raw.py` → 目視（用聯絡表）。退件改名保留，附原因重做。
5. 接進遊戲前先在**小尺寸**看一次（客人頭像、食材在氣泡裡是否分辨得出）。
6. 做**可重跑的測試**（含突變驗證）；寫成頁面，不要只留在對話裡。
7. 里程碑結束就寫報告／記憶，**換新對話**。
8. 每次遊戲更新美術都跑 `process_assets.py`（會更新版本戳）。
